# Internationalisation across backend and frontend

Sjodur has one message catalog for the whole system and one rule for where text is rendered:
**clients translate the UI; the backend speaks codes.**

## One source of truth

The catalogs live in `frontend/locales/de.json` and `frontend/locales/en.json`.

- The web frontend imports them directly (`frontend/locales/index.ts`, vue-i18n).
- The backend copies them into its jar at build time (`processResources` in `build.gradle`,
  see `build.gradle.additions.txt`) and reads them through `io.sjodur.i18n.Messages`.
- The mobile app will ship the same files.

`pnpm i18n:check` (also in CI) fails when a language misses or adds a key, when placeholders
differ between languages, or when a positional `{0}` sneaks in. German is the reference
language: add keys there first.

Conventions both sides understand:

| Convention | Example |
|---|---|
| dotted keys, nested in the JSON | `problem.not_found` |
| named placeholders only | `"Muss zwischen {min} und {max} Zeichen lang sein"` |
| plural forms as separate keys | `items.one`, `items.other` – chosen in code, no ICU syntax |
| no HTML in messages | components style the text |

The backend's `Messages.get(key, params)` and vue-i18n's `t(key, params)` render the same
string from the same file.

## The API speaks codes

Errors are RFC 9457 problem details (`ApiExceptionHandler`):

```json
{
  "status": 400,
  "title": "Das hat nicht geklappt",
  "detail": "Bitte prüfe deine Eingaben.",
  "code": "validation_failed",
  "errors": [
    { "field": "amount", "code": "min", "params": { "value": 0 }, "message": "Muss mindestens 0 sein" }
  ],
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

`code` maps to `problem.<code>` and field codes to `validation.<code>` in the catalog. The web
frontend translates them itself (`lib/problem.ts` → `useProblemText()`); `title`, `detail` and
`message` are the backend's rendering of the very same keys in the language negotiated via
`Accept-Language`, for clients that do not translate (curl, integrations, e-mail).

Why not let the backend translate everything? A user can switch the UI language without a
round trip, the mobile app needs its own catalog anyway, and a code is stable while wording
changes. Why not let only the clients translate? E-mails, exports and PDFs are rendered by
the backend, and a backend that can only say `not_found` is unpleasant to debug.

## Locale negotiation

- The web UI sends the chosen language as `Accept-Language` on every API call
  (`frontend/lib/api.ts`); the backend's `AcceptHeaderLocaleResolver` (`LocaleConfig`)
  narrows it to `de` or `en`, default `de`.
- Later: persist the preferred language in the user profile so e-mails use it too.
- Numbers, currencies and dates are formatted on the side that renders them, from the same
  locale tag (`de-DE`, `en-IE`): `Intl` in the browser (`lib/money.ts`), `java.text`/ICU
  data in Java. Both are CLDR-based, so `1.234,56 €` looks the same everywhere.

## Adding a language

1. Copy `de.json` to `<lang>.json` in `frontend/locales/`, translate, run `pnpm i18n:check`.
2. Add the locale to `supportedLocales` in `frontend/lib/i18n.ts` and to
   `Messages.SUPPORTED_LOCALES` in the backend.
3. Add it to `supportedLocales` in the Keycloak realm so the login page follows suit.
